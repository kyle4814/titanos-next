# Portal API production cutover (prepared 2026-11-13)

Status: IMPLEMENTED and TESTED in code. Nothing here has been run against Stripe, Resend or Cloudflare. Every step below is inert until the owner supplies the three items and says go.
Tags: OWNER = only the owner can do it. MACHINE = an agent can run it once the owner has supplied the inputs and approved the deploy.
No secret values and no new account identifiers are in this file. The D1 `database_id` already in `wrangler.toml` is the existing one.

## The three things only the owner can supply

1. OWNER: the Stripe LIVE key (the webhook signing secret is created by the MACHINE, see step 8). The Worker reads the key as `STRIPE_SECRET_KEY`; the value to put there is the owner's EXISTING restricted live key (`rk_live_...`, held locally under the env name `STRIPE_RESTRICTED_KEY`; the code accepts `sk_live_` and `rk_live_`). The signing secret (`whsec_...`, name `STRIPE_WEBHOOK_SECRET`) does not exist yet: the MACHINE creates the endpoint and stores the secret in step 8, so the owner supplies nothing for it.
2. OWNER: a Resend account with a verified sending domain, an API key and the sender address (secret `RESEND_API_KEY`, var `MAIL_FROM`).
3. OWNER: the go-word and date for arming live billing (var `LIVE_BILLING_ARMED`, format `yes-YYYY-MM-DD`) plus approval to deploy and to bind `portal-api.titanos.tech` (the titanos.tech zone must be on the Cloudflare account used to deploy).

Machine-generated by the MACHINE, never supplied by the owner: `INTERNAL_API_SECRET`, `RECEIPT_SECRET`, optional `SSO_SEAL_KEYS` (random values created at set time, piped straight into wrangler, never printed).

## Where each name is read

| Name | Kind | Read in | If missing |
|---|---|---|---|
| `STRIPE_MODE` | var | `src/build_deps.ts` | "test" behaviour |
| `STRIPE_SECRET_KEY` | secret | `billingFor`, `assertLiveArmed` | live refuses to start (`live_not_armed`) |
| `STRIPE_WEBHOOK_SECRET` | secret | `buildDeps` -> `/stripe/webhook` | live refuses to start |
| `MAIL_PROVIDER` (`resend`), `RESEND_API_KEY`, `MAIL_FROM` | var, secret, var | `mailerFor`, `src/mail.ts` | live refuses to start |
| `LIVE_BILLING_ARMED` | var | `assertLiveArmed` | live refuses to start |
| `INTERNAL_API_SECRET` | secret | `buildDeps` (operator trace and internal market/enterprise routes) | those routes answer 401 |
| `RECEIPT_SECRET` | secret | `buildDeps` (agent receipts) | receipts unsigned as today |
| `SSO_SEAL_KEYS` | secret | `sealKeysOf` | SSO config answers 503 |
| `TITANOS_EXTRA_ORIGINS` | var | `cors` in `src/index.ts` | only `TITANOS_SITE_ORIGIN` is allowed |

A refused start returns 503 `{"error":"deps_unavailable","reason":"live_not_armed:<names missing>"}` (names only). `/health` stays up.

## Restricted key permissions (read from `src/stripe.ts`; this Worker makes exactly these Stripe calls)

| Call | Used for | Stripe resource permission needed |
|---|---|---|
| `POST /v1/checkout/sessions` | `/checkout`, credit top-ups | Checkout Sessions: Write |
| `GET /v1/checkout/sessions/{id}?expand[]=subscription` | pending-purchase reconciler | Checkout Sessions: Read, Subscriptions: Read |
| `POST /v1/subscriptions/{id}` (cancel at period end) and `DELETE /v1/subscriptions/{id}` | subscription cancel | Subscriptions: Write |
| `POST /v1/refunds` | refunds | Charges and Refunds: Write (PaymentIntents: Read is harmless to add) |
| `POST /v1/billing_portal/sessions` | `/billing` portal link | Customer portal: Write |

Nothing else is called (marketplace Connect calls in `src/market/payments.ts` are not used in live mode). Confirm in the dashboard (Developers > API keys > the key > permissions) that each row above is set; everything else may stay "None".
If a permission is missing Stripe answers 403. `/checkout` then logs `checkout failed: stripe returned 403 (check the Stripe key's permissions in the dashboard)` (status only, never the key) and the visitor sees a retryable 503 `billing_unavailable`; no mock link and no success is ever shown (tested). Fix the scope in the dashboard and retry; no redeploy is needed. Refund, cancel and portal calls still throw a plain error on a Stripe refusal (a generic 500 to the caller, nothing recorded as done); that wording is a known gap listed below.

## Ordered steps

All commands run from `portal-api/`. Use `npx wrangler` if wrangler is not installed. Secrets use hidden input (wrangler prompts; nothing goes on the command line or in shell history).

1. MACHINE: confirm the branch is merged and `npm test` is green (see Verify below). Confirm `git status` is clean.
2. OWNER: supply the three items above.
3. MACHINE: back up. `npx wrangler d1 export titanos-portal --remote --output <path outside the repo>` (read-only on the database). Record the currently deployed version id: `npx wrangler deployments list`.
4. OWNER: in the Stripe dashboard (LIVE mode) confirm the restricted key's permissions (section above) AND that it also has "Webhook Endpoints: Write" (needed only by the registration script in step 8). The owner does NOT create the webhook by hand.
5. MACHINE (with the owner's values): set secrets, each with a hidden prompt:
   `npx wrangler secret put STRIPE_SECRET_KEY` (value: the owner's existing restricted live key), `RESEND_API_KEY`, `INTERNAL_API_SECRET`, `RECEIPT_SECRET`, and optionally `SSO_SEAL_KEYS`. `STRIPE_WEBHOOK_SECRET` is set by step 8, not here.
   Generate the machine secrets with `openssl rand -hex 32` piped to `wrangler secret put <NAME>` so the value is never displayed.
6. MACHINE: edit `wrangler.toml` as the comments at the bottom say: `STRIPE_MODE = "live"`, delete `DEV_OUTBOX`, add `TITANOS_EXTRA_ORIGINS`, `MAIL_PROVIDER`, `MAIL_FROM`, `LIVE_BILLING_ARMED`, and uncomment the `routes` line for `portal-api.titanos.tech`. Do not commit a real sender or date to main without the owner's go.
7. MACHINE: apply migrations to the remote D1: `npx wrangler d1 migrations list titanos-portal --remote`, then `npx wrangler d1 migrations apply titanos-portal --remote`. The migration set is whatever is on main at that time (the subscribe and booking lanes renumber theirs), so list first and read what will run.
8. MACHINE (after the owner's deploy approval): register the Stripe webhook and store its signing secret in one go. First `node scripts/register_stripe_webhook.mjs --hostname portal-api.titanos.tech --confirm-live portal-api.titanos.tech --dry-run` and read the masked plan, then run it without `--dry-run`. It reads the key from `$STRIPE_SECRET_KEY` (or the variable named by `--key-env`; export it in the shell for this one command, never on the command line), refuses a non-live key or a host mismatch, lists existing endpoints first (a match on the same URL changes nothing), otherwise creates `https://portal-api.titanos.tech/stripe/webhook` for exactly `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `invoice.paid`, `customer.subscription.deleted`, `charge.refunded` (the only event types the handler consumes; pinned by `test/register_stripe_webhook.test.ts`), and pipes the returned signing secret on stdin into `npx wrangler secret put STRIPE_WEBHOOK_SECRET` (never on disk, terminal or logs). Exit codes: 2 refused, 3 key lacks permission (it names the missing Stripe permission), 4 Stripe error, 5 endpoint created but the secret was not stored (reveal it in the dashboard and `wrangler secret put` it by hand). Run it BEFORE the deploy so the Worker starts armed with the secret already set.
9. MACHINE: `npx wrangler deploy`. This binds the custom domain `portal-api.titanos.tech`. The old `titanos-api` Worker and `api.titanos.tech` are not touched.
10. MACHINE: smoke test the Worker directly (below) before the site changes.
11. MACHINE: rebuild the site with the new base: `NEXT_PUBLIC_PORTAL_API_BASE=https://portal-api.titanos.tech npm run build` in the repo root, then publish the static `out/` by the site's normal deploy path (owner approval). The default build (variable unset) still points at `https://api.titanos.tech`.
12. OWNER: one real purchase of the lowest-priced product with your own card, then refund it from the dashboard. This is the only proof that live money works end to end.
13. MACHINE: watch `npx wrangler tail` for `buildDeps refused` and `mail_` errors for the first day.

## Smoke test list (steps 10 and 13; none writes data beyond a login token)

- `GET https://portal-api.titanos.tech/health` -> 200, `stripe_mode":"live"`, `db":"ok"`.
- `GET /catalogue` -> 200 and the product list (proves buildDeps armed; a 503 `live_not_armed:...` names what is missing).
- `OPTIONS /auth/request` with `Origin: https://titanos.tech` and again with `https://www.titanos.tech` -> `access-control-allow-origin` echoes each; with `https://evil.example` it returns `https://titanos.tech`.
- `POST /auth/request` with an owner-controlled address -> 202 and the login mail arrives from `MAIL_FROM` (a 503 `mail_unavailable` is retryable; a 502 `mail_rejected` means fix the Resend key or sender domain).
- Open the link, `POST /auth/verify`, `GET /me` -> 200; `POST /auth/logout` -> 200; `GET /me` with the same token -> 401.
- `GET /internal/keys/trace?prefix=tk_x` with header `x-operator-secret` set to the secret -> 200; without it -> 401.
- `POST /stripe/webhook` with a bad signature -> 400. Use the Stripe dashboard "send test webhook" for a signed delivery -> 200.
- `POST /checkout` as a signed-in user returns a `checkout.stripe.com` URL (no mock host) and does not complete a payment.
- Marketplace job funding and payouts answer 503 `payments_unavailable` / `payouts_unavailable` in live mode (out of scope here).

## Rollback

- Site: rebuild without `NEXT_PUBLIC_PORTAL_API_BASE` (default is `https://api.titanos.tech`) and republish.
- Worker: `npx wrangler rollback <version id from step 3>`; or remove the `routes` line and redeploy; or set `LIVE_BILLING_ARMED` to an invalid value (`npx wrangler secret`-free: edit the var, deploy) so the Worker refuses to start live billing at once. Stripe: disable the live webhook endpoint in the dashboard.
- Data: migrations are forward-only; restore from the step 3 export only with the owner's approval (irreversible).
- Test-mode fallback: put `STRIPE_MODE = "test"` and `DEV_OUTBOX = "1"` back and redeploy.

`cd portal-api && npm test` (migration_lint, d1_debt_gate, all tests). Live-mode guards are in `test/production_path.test.ts`; the site base is in `scripts/test_portal_api_base.mjs`.

## Known limits

- Only `/checkout` maps a Stripe refusal to the clear `billing_unavailable` answer; refund, cancel and portal paths were left as they were.
- The Resend API shape was read from the provider's public docs on 2026-11-13; no real request has ever been sent.
- `/health` reports `stripe_mode` from the var alone, so a refused live start still shows "live" there; the 503 reason on any other route is the truth.
- Logout expires the session row rather than deleting it (no Store interface change); the site keeps its token in localStorage, so the cookie clear is a harmless extra.
